## 🧱 第二站：创建型模式（5 GoF + 1 非GoF）背诵卡片

> 📖 **创建型总纲（选择题高频）**：
> - 核心思想：将**对象的创建过程和使用过程分离**，隐藏实例化细节，符合**单一职责原则**。
> - 回答的 3 个问题：**创建什么（What）？由谁创建（Who）？何时创建（When）？**
> - PPT 提到的 Java 创建对象的 4 种方式：`new` 关键字、工厂类、**反射机制**（`Class.forName(cName).newInstance()`）、**克隆方法 `clone()`**。

---

### 1. 简单工厂模式（Simple Factory）—— 唯一非 GoF（+1）
- **分类与地位**：**非 GoF 23 种设计模式**之一（编程习惯），属于**类创建型模式**；别名**静态工厂方法（Static Factory Method）模式** / **上帝类**。
- **官方定义（背诵）**：定义一个工厂类，它**可以根据参数的不同返回不同类的实例**，被创建的实例通常都**具有共同的父类**。（核心工厂方法通常定义为 `static`）。
- **核心角色（3 个）**：
  1. `Factory`（工厂角色）：核心，含静态方法 `factoryMethod(String type)`，内部用 `if-else/switch` 判断创建对象；
  2. `Product`（抽象产品角色）：所有产品共同的父类/接口；
  3. `ConcreteProduct`（具体产品角色）：具体创建目标。
- **优缺点 & 设计原则**：
  - ✅ **优点**：分离创建与使用；客户端只需记**参数**无需记类名；配合 XML 配置文件更换产品不改客户端。
  - ❌ **缺点（必背原话）**：① 工厂类集中所有创建逻辑，**职责过重**；② 增加类的个数；③ **系统扩展困难，一旦添加新产品不得不修改工厂逻辑，违背开闭原则（OCP）**；④ 静态方法导致工厂无法形成继承等级结构。
- **PPT 案例 & JDK 应用**：
  - 案例：多种支付方式（CashPay/CreditcardPay）、简单电视机工厂（Haier/Hisense）、统计图表工厂（柱/饼/折线）。
  - JDK 应用：**`java.text.DateFormat.getDateInstance()`**（`KeyGenerator`、`Cipher` 等静态工厂）。
- **考场秒杀坑**：问“以下不属于 GoF 23 种模式的是？” -> **简单工厂模式**；问“简单工厂结构有抽象工厂吗？” -> **没有！只有具体工厂+抽象产品+具体产品**（2024 真题第 9 题）。

---

### 2. 工厂方法模式（Factory Method）
- **分类与地位**：GoF **类创建型**模式；简称**工厂模式**，别名**虚拟构造器（Virtual Constructor）模式** / **多态工厂（Polymorphic Factory）模式**。
- **官方定义（背诵）**：定义一个用于创建对象的接口，但是**让子类决定将哪一个类实例化**。工厂方法模式**让一个类的实例化延迟到其子类**。
- **核心角色（4 个）**：
  1. `Product`（抽象产品）
  2. `ConcreteProduct`（具体产品）
  3. `Factory`（抽象工厂）：**核心角色**，声明动态的工厂方法 `factoryMethod()`；
  4. `ConcreteFactory`（具体工厂）：一一对应生成具体产品（`return new ConcreteProduct();`）。
- **优缺点 & 设计原则**：
  - ✅ **优点**：向客户隐藏实例化细节；**增加新产品时只需增加具体产品类和具体工厂类，完全符合开闭原则（OCP）**；可配合 **XML + Java 反射（`Class.forName().newInstance()`）** 实现零修改客户端。
  - ❌ **缺点**：新增产品时**系统中类的个数成对增加（类爆炸）**，增加系统复杂度和抽象性。
- **PPT 案例 & JDK 应用**：
  - 案例：支付方式工厂拆分、品牌电视机分厂（HaierTVFactory / HisenseTVFactory）、农场培育水果（苹果/葡萄/草莓）。
  - 重点技术：PPT 本章难点强调 **DOM 解析 XML + Java 反射创建对象**（`XMLUtil.getBean()`）。
- **考场秒杀坑**：工厂方法的核心是**抽象工厂类（动态方法）**，而简单工厂的核心是**具体工厂类（静态方法）**。

### 3. 抽象工厂模式（Abstract Factory）
- **分类与地位**：GoF **对象创建型**模式；别名 **Kit 模式**。
- **两个核心概念（填空/选择必考）**：
  - **产品等级结构**：产品的**继承结构**（纵向同一个品类，如：抽象电视机 -> 海尔电视、TCL 电视）。
  - **产品族**：由**同一个工厂生产的、位于不同产品等级结构中的一组产品**（横向同一品牌全家桶，如：海尔电视机 + 海尔电冰箱 + 海尔空调）。
- **官方定义（背诵）**：**提供一个创建一系列相关或相互依赖对象的接口，而无须指定它们具体的类**。
- **核心角色（4 个）**：`AbstractFactory`（声明 `createProductA()`、`createProductB()` 等多个方法）、`ConcreteFactory`（如海尔工厂生产一族电器）、`AbstractProduct`、`ConcreteProduct`。
- **优缺点 & 开闭原则的“倾斜性”（PPT 本章最大难点！）**：
  - ✅ **优点**：隔离具体类生成；**保证客户端始终只使用同一个产品族中的对象**；**增加新的产品族很方便，符合开闭原则**。
  - ❌ **缺点**：**增加新的产品等级结构麻烦**（需要修改抽象工厂接口及所有具体工厂类），**严重违背开闭原则**。
- **PPT 案例**：跨 OS 图形界面（Button + TextField）、海尔/TCL 电器工厂（电视+空调）、奔驰/宝马汽车族（轿车+SUV+MPV）。
- **🔥 三种工厂模式终极对比（简答/选择秒杀）**：
  | 模式 | 生产粒度 | 工厂方法性质 | 扩展产品（加等级/加品类） | 扩展产品族 |
  | :--- | :--- | :--- | :--- | :--- |
  | **简单工厂** | 同一等级中**任意**产品（多选一） | 静态（`static`） | ❌ 改工厂（违背 OCP） | 不支持 |
  | **工厂方法** | 同一等级中**固定**产品（一对一） | 动态（分布在子类） | ✅ 增工厂+产品（符合 OCP） | 不支持（类太多） |
  | **抽象工厂** | **不同产品族的全部产品**（一对多族） | 动态（一工厂多方法） | ❌ **改抽象接口（违背 OCP）** | ✅ **增新具体工厂（符合 OCP）** |

### 4. 建造者模式（Builder）
- **分类与地位**：GoF **对象创建型**模式（**最复杂**的创建型模式，难度 ★★★★★）。
- **官方定义（背诵）**：将**一个复杂对象的构建与它的表示分离**，使得**同样的构建过程可以创建不同的表示**。（一步一步创建复杂对象，用户只需指定类型和内容，无需知道内部装配细节）。
- **核心角色（4 个）**：
  1. `Builder`（抽象建造者）：声明创建各个部件的抽象方法（`buildPartA/B/C`）和返回最终产品的方法（`getResult()`）；
  2. `ConcreteBuilder`（具体建造者）：实现各部件具体组装逻辑；
  3. `Product`（产品角色）：包含多个组成部分的复杂对象；
  4. `Director`（指挥者角色）：**核心亮点**，安排复杂对象的**建造次序/构建流程**，隔离客户端与创建过程（先做 A 再做 B 后做 C，防漏装、防顺序错）。
- **优缺点 & 适用场景**：
  - ✅ **优点**：解耦产品本身与创建过程；具体建造者相互独立，增替方便（符合 OCP）；**更精细地控制产品创建过程**。
  - ❌ **缺点**：要求产品组成部分相似（差异太大不适用）；内部变化太复杂会导致具体建造者过多。
  - 💡 **模式简化（PPT 扩展）**：只有 1 个具体建造者时可省略抽象建造者，甚至继续省略指挥者让 `Builder` 身兼双职。
- **PPT 案例 & JDK 应用**：
  - 案例：KFC 套餐装配（主食+饮料）、游戏角色（Angel/Hero/Devil 的性别/面容/服装/发型）、汽车装配。
  - 应用：**JavaMail**（`Message` / `MimeMessage`）、游戏地图/人物生成。
- **考场秒杀坑**：工厂模式关注**“生产出什么产品（整体）”**；建造者模式关注**“复杂对象各部件如何分步骤装配（流程/顺序）”**。

### 5. 原型模式（Prototype）
- **分类与地位**：GoF **对象创建型**模式（简单程度**仅次于单例模式**和迭代器模式——2023 真题填空原话！）。
- **官方定义（背诵）**：**使用原型实例指定待创建对象的类型，并且通过复制（克隆）这个原型来创建新的对象**。
- **核心角色（3 个）**：`Prototype`（抽象原型类，声明克隆方法）、`ConcretePrototype`（具体原型类，实现 `clone()`）、`Client`（客户类）。
- **Java 核心实现机制（必背高频！）**：
  - 原型模式的“工厂”就是**原型类自身**，“工厂方法”就是**克隆方法**，**绕过了构造方法**。
  - **`Cloneable` 接口**：位于 `java.lang`，是一个**空接口 / 标识接口**（Marker Interface），仅告诉 JRE 该类支持克隆；未实现却调 `Object.clone()` 会抛出 `CloneNotSupportedException`。
  - **浅克隆 vs 深克隆（必背对比！）**：
    - **浅克隆（Shallow Clone）**：重写 `Object.clone()`。只复制**对象本身**和**8种基本类型成员变量**；**引用类型成员变量只复制引用地址**（原对象和克隆对象共享同一个内部引用对象）。*（注：`String` 因不可变性，表现像值拷贝互不影响）*。
    - **深克隆（Deep Clone）**：对象本身 + **所有引用类型的成员变量都递归复制**。Java 最常用方式：**对象序列化与反序列化**（写入 `ObjectOutputStream` 再由 `ObjectInputStream` 读出），要求原型类及**所有引用成员类都必须实现 `Serializable` 标识接口**。
  - **`clone()` 三条性质**：`x.clone() != x`（地址不同返回 `false`）、`x.clone().getClass() == x.getClass()`、`x.clone().equals(x)` 成立。
- **优缺点 & 扩展**：
  - ✅ **优点**：简化创建过程、提高效率（无需走复杂构造）；扩展性好；简化创建结构；深克隆可保存对象状态辅助**撤销操作**。
  - ❌ **缺点**：需为每个类配克隆方法，**改造已有类需改源码，违背 OCP**；深克隆多重嵌套引用实现繁琐。
  - 扩展：**带原型管理器的原型模式**（用一个 `Hashtable` 存多个原型对象，按 key 取出来 `.clone()`）。
- **PPT 案例 & 框架应用**：邮件复制（不复制附件=浅克隆；同时复制附件=深克隆）、工作周报复制、发奖状；复制粘贴、Spring 中原型 bean（`scope="prototype"`）、Struts2 Action。

---

### 6. 单例模式（Singleton）
- **分类与地位**：GoF **对象创建型**模式（结构**最简单**的设计模式，只包含一个特殊类）。
- **官方定义 & 三大要点（必背！）**：
  - 定义：确保**某一个类只有一个实例**，而且**自行实例化**并**向整个系统提供这个实例**。
  - 三要点：**① 某个类只能有一个实例；② 必须自行创建这个实例；③ 必须自行向整个系统提供这个实例**。
- **代码实现“三私一公”灵魂**：
  1. **私有构造函数**（`private Singleton()`）——防外部 `new`；
  2. **静态私有自身类型成员变量**（`private static Singleton instance`）——自行保存唯一实例；
  3. **静态公有工厂方法**（`public static Singleton getInstance()`）——全局唯一访问点。
- **五大写法与面试/考场必背对比**：
  | 实现方式 | 实例化时机 | 线程安全？ | 核心关键字 / 原理 |
  | :--- | :--- | :-: | :--- |
  | **饿汉式（Eager）** | **类加载时**即创建 | ✅ 天生安全 | `private static final Singleton instance = new Singleton();`（响应快但可能浪费内存） |
  | **懒汉式（普通）** | **首次调用 `getInstance()`** 时 | ❌ 不安全 | 多线程同时进入 `if (instance == null)` 会创建多个实例 |
  | **懒汉式（锁方法）** | 首次调用时 | ✅ 安全 | 方法加 `synchronized`（粒度太大，每次获取都要排队，性能低） |
  | **双重检查锁定（DCL）** | 首次调用时 | ✅ 安全 | **两次 `if (instance == null)`** + **`synchronized(Singleton.class)`** + 成员变量加 **`volatile`**（保证**内存可见性**、禁止指令重排，JDK 1.5+） |
  | **静态内部类（IoDH）** | 首次调用时 | ✅ 安全 | `private static class HolderClass { private final static Singleton instance = new Singleton(); }`，兼顾延迟加载与线程安全（JVM 保证类初始化锁） |
- **优缺点 & 设计原则**：
  - ✅ **优点**：受控访问唯一实例；节约系统资源；可扩展为有限个实例（**多例模式**）。
  - ❌ **缺点**：**没有抽象层，扩展困难**；**职责过重，与单一职责原则（SRP）冲突**（把“业务”和“控制单例”混在一起）；自动垃圾回收机制可能导致无状态单例状态丢失。
- **PPT 案例 & JDK 应用**：
  - 案例：Windows 任务管理器、操作系统**打印池（Print Spooler）**、**身份证号码（补办还是原号）**、多线程游戏 Boss。
  - JDK/框架应用：**`java.lang.Runtime`（`Runtime.getRuntime()` 饿汉式）**、数据库自增主键生成器、**Spring IoC 容器默认 Bean 作用域（`scope="singleton"`）**。

---

## 🏗️ 第三站：结构型模式（6 GoF）背诵卡片

> 📖 **结构型总纲**：
> - 主要作用：将不同的**类和对象组合**在一起形成更大的结构。
> - 分为**类结构型模式**（只存在**继承**和**实现**关系）与**对象结构型模式**（通过**关联/聚合**组合实例）。根据**合成复用原则**，绝大多数是对象结构型模式。

---

### 7. 适配器模式（Adapter）
- **分类与地位**：GoF 结构型模式（**唯一既可以是类结构型，也可以是对象结构型**的模式）；别名**包装器（Wrapper）模式**。
- **官方定义（背诵）**：**将一个接口转换成客户希望的另一个接口**，使接口不兼容的那些类可以一起工作。（对现有系统进行**补救**和现有类**重用**的模式）。
- **核心角色（3 个）**：
  1. `Target`（目标抽象类）：客户所期待的接口；
  2. `Adaptee`（适配者类/源角色）：已存在的、接口不兼容但功能可用的类；
  3. `Adapter`（适配器类）：把源接口转换成目标接口的包装类。
- **两大实现对比（必背大题/选择高频！）**：
  | 对比维度 | 类适配器（Class Adapter） | 对象适配器（Object Adapter） |
  | :--- | :--- | :--- |
  | **底层关系** | **继承** `Adaptee` + **实现** `Target` | **实现/继承** `Target` + **内部关联/聚合** `Adaptee` 对象 |
  | **设计原则** | **违背合成复用原则（CRP）** | **符合合成复用原则（CRP）**，推荐优先使用 |
  | **适配能力** | 一次**只能适配一个**适配者（Java 单继承）；目标必须是接口；适配者不能是 `final` 类 | 可同时**把多个适配者适配到同一目标**，也可适配适配者的**子类** |
  | **方法置换** | 继承关系，在适配器中重写/置换适配者方法**方便** | 置换适配者原有方法**较麻烦** |
- **两个重要扩展（PPT 10.6 重点）**：
  - **缺省适配器模式（单接口适配器模式）**：当不想实现一个大接口的所有方法时，设计一个**抽象类实现该接口并提供空方法**，子类只需选择性覆盖（解决接口臃肿，如 Java AWT 中的 `WindowAdapter`）。
  - **双向适配器模式**：同时实现 `Target` 和 `Adaptee` 接口并持有双方引用，支持双向互操作。
- **PPT 案例 & JDK 应用**：电源适配器（220V 转 20V）、仿生机器人（学狗叫狗跑）、儿童玩具车（重用警灯警笛）；**JDBC 驱动程序**、JDK `InputStreamAdapter`。

---

### 8. 桥接模式（Bridge）
- **分类与地位**：GoF **对象结构型**模式；别名**柄体（Handle and Body）模式** / **接口（Interface）模式**。
- **官方定义（背诵）**：**将抽象部分与它的实现部分分离（解耦），使它们都可以独立地变化**。（用**抽象关联取代传统的多重/多层继承**，将类之间的静态继承关系转换为动态的对象组合关系）。
- **核心动机（秒杀题眼）**：当一个类存在**两个（或多个）独立变化的维度**时，用继承会导致类数量呈**乘法爆炸**（3×12=36支蜡笔）；桥接模式把“乘法变成加法”（3支毛笔+12种颜料=15个类）。
- **核心角色（4 个）**：
  1. `Abstraction`（抽象类）：主维度父类，**内部聚合一个 `Implementor` 接口引用**（那座“桥”）；
  2. `RefinedAbstraction`（扩充抽象类）：主维度的具体子类；
  3. `Implementor`（实现类接口）：副维度接口；
  4. `ConcreteImplementor`（具体实现类）：副维度的具体实现。
- **优缺点 & 设计原则**：
  - ✅ **优点**：分离抽象与实现；取代多层继承，**极大减少子类个数**；任意扩展任一维度都**符合开闭原则**；体现 OCP、CRP、LSP、DIP。
  - ❌ **缺点**：增加理解与设计难度（关联建在抽象层）；**正确识别出两个独立变化的维度较困难**。
- **PPT 案例 & JDK 应用**：
  - 案例：**毛笔与蜡笔的故事**、**跨平台图像浏览系统**（文件格式 BMP/JPG/PNG × 操作系统 Win/Linux/Unix）、你的视频播放器（操作系统 Win/Mac × 视频格式 Mp4/Avi）。
  - 应用：**JVM 平台无关性**、Java AWT `Peer` 架构、**JDBC 驱动程序**（应用系统 vs 具体数据库）。
- **与适配器联用**：**桥接用于系统初期设计**（分离两维度）；设计完成后发现与已有第三方类接口不兼容，再配合**适配器模式**接入。

---

### 9. 组合模式（Composite）
- **分类与地位**：GoF **对象结构型**模式。
- **官方定义（背诵）**：组合多个对象形成**树形结构**以表示**“部分-整体”**的层次结构。组合模式对**单个对象（叶子对象）**和**组合对象（容器对象）**的使用具有**一致性**。
- **核心角色（3 个）**：
  1. `Component`（抽象构件）：为叶子和容器声明统一接口；
  2. `Leaf`（叶子构件）：树的最底层，不能包含子成员；
  3. `Composite`（容器构件）：内部维持 `ArrayList<Component>` 子构件集合，调用业务方法时会**递归调用**其所有子构件的业务方法。
- **🔥 透明组合模式 vs 安全组合模式（2023 真题简答原题！必背！）**：
  | 对比点 | 透明组合模式（Transparent） | 安全组合模式（Safe） |
  | :--- | :--- | :--- |
  | **`add/remove/getChild` 声明在哪** | 声明在**抽象构件 `Component`** 中 | 只声明在**容器构件 `Composite`** 中 |
  | **优点** | **透明性好**：客户端完全面向抽象编程，对叶子和容器一视同仁 | **安全性好**：叶子根本没有这些方法，误调用在**编译期**就会报错拦截 |
  | **缺点** | **不够安全**：叶子调用 `add()` 无意义，只能抛异常（运行期才报错） | **不够透明**：客户端无法完全面向抽象，必须区分强转叶子和容器 |
- **优缺点 & 应用**：
  - ✅ **优点**：清楚定义分层次复杂对象；简化客户端代码（忽略层次差异）；增新容器/叶子符合 OCP；灵活处理树形结构。
  - ❌ **缺点**：设计抽象；**新增构件时很难对容器中的构件类型进行限制**（只能运行期判断）。
  - 案例与 JDK：**水果盘**（盘套盘+水果）、**杀毒软件**（文件夹套文件夹+各种文件）、XML 文档解析；**JDK AWT/Swing GUI（`Component` 与 `Container`）**。

---

### 10. 装饰模式（Decorator）
- **分类与地位**：GoF **对象结构型**模式。
- **官方定义（背诵）**：**动态地给一个对象增加一些额外的职责**，就增加对象功能来说，装饰模式**比生成子类实现更为灵活**。（一种**用于替代继承**的技术，用对象之间的关联关系取代继承关系）。
- **核心角色（4 个）**：
  1. `Component`（抽象构件）
  2. `ConcreteComponent`（具体构件）：被装饰的原始对象；
  3. `Decorator`（抽象装饰类）：**代码灵魂——既继承 `Component`，内部又聚合一个 `Component` 引用**（为了能像套娃一样层层嵌套且对客户透明）；
  4. `ConcreteDecorator`（具体装饰类）：在调用 `super.operation()` 前后加上新方法 `addedBehavior()`。
- **🔥 透明装饰模式 vs 半透明装饰模式（PPT 本章难点！选择/填空高频！）**：
  | 对比点 | 透明装饰模式 | 半透明装饰模式 |
  | :--- | :--- | :--- |
  | **客户端如何声明对象** | **全部声明为抽象构件 `Component` 类型** | 原始构件用 `Component`，装饰后**用具体装饰类 `ConcreteDecorator` 声明** |
  | **能否多次嵌套装饰** | ✅ **可以对同一个对象进行多次装饰**（套娃） | ❌ **不能**对同一对象多次装饰（因为类型已变为具体装饰类） |
  | **能否单独调用新增方法** | ❌ **不能**在客户端单独调用 `addedBehavior()` | ✅ **可以**在客户端单独调用 `addedBehavior()` |
- **优缺点 & JDK 应用**：
  - ✅ **优点**：比继承灵活（不会类爆炸）；运行时动态扩展功能；可多次装饰；具体构件和具体装饰独立变化（符合 OCP）。
  - ❌ **缺点**：产生很多**小对象**占内存；**排错困难**（多层嵌套需逐级排查）。
  - 案例与 JDK：变形金刚（汽车->加说话->加飞翔）、图形界面构件库（加滚动条/黑边框）；**`java.io` 流体系（`new BufferedInputStream(new FileInputStream(...))`）**、Swing `new JScrollPane(list)`。

---

### 11. 外观模式（Facade）
- **分类与地位**：GoF **对象结构型**模式（使用频率极高 ★★★★★，难度最低 ★☆☆☆☆）；别名**门面模式**。
- **官方定义（背诵）**：外部与一个子系统的通信必须通过一个**统一的外观对象**进行，为**子系统中的一组接口提供一个统一的入口**。外观模式定义了一个**高层接口**，这个接口使得这一子系统更加容易使用。
- **核心角色（2 个）**：
  1. `Facade`（外观角色）：聚合各个子系统对象，编排对外提供的统一简化方法（注意：**不要试图通过外观类为子系统增加新行为**，只做转发和组合编排！）；
  2. `SubSystem`（子系统角色）：各自独立的业务类/模块（如 `FileReader`、`CipherMachine`、`FileWriter`）。
- **优缺点 & 设计原则**：
  - ✅ **核心原则**：**迪米特法则（最少知识原则）的最典型体现**！
  - ✅ **优点**：对客户端屏蔽子系统组件，**减少客户端所需处理的对象数目**；实现客户端与子系统之间的**松耦合**；子系统内部变化不影响客户端（只需改外观类）。
  - ❌ **缺点**：**不能很好地限制客户端直接使用子系统类**；设计不当时，**增加/更换子系统需要修改外观类源码，违背开闭原则（OCP）**。
  - 💡 **模式扩展**：引入**抽象外观类（`AbstractEncryptFacade`）** + 配置文件，可以在更换子系统时增加新外观子类而不改老代码，从而**在一定程度上解决违背 OCP 的问题**。一个系统也可以有多个外观类。
- **PPT 案例 & 真题应用**：公司前台、电源总开关/智能家居控制、**文件加密模块（2024 年期末压轴大题原题！）**；**JDBC 工具类封装**、`JavaEE Session 外观模式`。

---

### 12. 代理模式（Proxy）
- **分类与地位**：GoF **对象结构型**模式。
- **官方定义（背诵）**：给某一个对象**提供一个代理**，并**由代理对象控制对原对象的引用**。（客户与目标之间的中介，可去掉客户不能看的内容或添加额外服务）。
- **核心角色（3 个）**：
  1. `Subject`（抽象主题）：声明真实主题和代理主题的共同接口；
  2. `RealSubject`（真实主题）：真正执行业务逻辑的对象；
  3. `Proxy`（代理主题）：维持一个 `RealSubject` 引用，在调用真实方法前后加上 `preRequest()` / `postRequest()` 控制逻辑。
- **🔥 常用代理类型（2023 真题简答原题！必背！）**：
  1. **保护代理（Protect Proxy）**：控制访问权限，给**不同用户提供不同级别权限**（如：论坛注册用户 vs 游客；⚠️ 会降低一点处理速度）；
  2. **远程代理（Remote Proxy / 大使 Ambassador）**：为不同地址空间的对象提供本地代理，**隐藏网络通信细节**（如 **Java RMI 中的 Stub 存根**、EJB、RPC）；
  3. **虚拟代理（Virtual Proxy）**：对资源消耗大的对象，先用小代理对象占位，**真正需要时再创建真实对象**（以时间换空间，如网页大图懒加载；变体：**Copy-on-Write 代理**，深克隆延迟到真正用到时）；
  4. **缓冲代理（Cache Proxy）**：为某目标操作结果提供**临时存储空间**以便共享结果；
  5. **智能引用代理（Smart Reference Proxy）**：引用对象时提供额外操作（如统计调用次数、收费商务查询记录日志）。
  - *（另：防火墙代理、同步化代理）*
- **优缺点 & JDK/框架应用**：
  - ✅ **优点**：协调调用与被调用者，降低耦合；客户端面向 `Subject` 编程，**增换代理类无需改源码，符合 OCP**。
  - ❌ **缺点**：部分代理（如保护代理）**处理速度变慢**；部分代理（如远程代理）实现复杂。
  - 应用：**Java RMI（Stub 桩）**、**Spring AOP（底层是动态代理：JDK `java.lang.reflect.Proxy.newProxyInstance` + `InvocationHandler.invoke()`）**、火车票代售点。

---

### 🔥 结构型“四大易混包装器”秒杀对比表
| 模式 | 核心关键词 | 接口是否改变？ | 目的 | 典型比喻/案例 |
| :--- | :--- | :--- | :--- | :--- |
| **适配器 (Adapter)** | **转换 / 兼容** | ✅ **改变接口**（把 A 转成 B） | 补救不兼容，重用已有类 | 电源转接头、JDBC 驱动 |
| **装饰 (Decorator)** | **增强 / 嵌套** | ❌ **保持原接口** | 动态**叠加**新功能（不改原类） | Java I/O 流套娃、加黑框滚动条 |
| **代理 (Proxy)** | **控制 / 替身** | ❌ **保持原接口** | **控制访问**（鉴权/延迟/远程/日志） | 论坛权限、Spring AOP、火车代售点 |
| **外观 (Facade)** | **简化 / 门面** | ✅ **简化高层入口** | 隐藏子系统复杂性（一拖多） | 电源总开关、文件加密门面 |

## ⚡ 第四站：行为型模式（5 GoF）背诵卡片

> 📖 **行为型总纲**：
> - 主要作用：描述**类或对象如何交互、怎样分配职责**，以及复杂流程控制。
> - 分为类行为型（继承/多态分配职责）与对象行为型（聚合关联分配职责）。**我们所学的这 5 种全部都是对象行为型模式！**

---

### 13. 命令模式（Command）
- **分类与地位**：GoF **对象行为型**模式；别名**动作（Action）模式** / **事务（Transaction）模式**。
- **官方定义（背诵）**：**将一个请求封装为一个对象**，从而使我们可用**不同的请求对客户进行参数化**；对**请求排队**或者**记录请求日志**，以及**支持可撤销的操作**。
- **核心角色（4 个）**：
  1. `Command`（抽象命令类）：声明执行方法 `execute()`（以及可选的 `undo()`）；
  2. `ConcreteCommand`（具体命令类）：**内部维持对 `Receiver` 接收者的引用**，在 `execute()` 中调用 `receiver.action()`；
  3. `Invoker`（调用者 / 请求发送者）：持有 `Command`（不直接认识 `Receiver`！），只负责发起 `command.execute()`；
  4. `Receiver`（接收者）：真正干活执行请求的类。
- **三大核心扩展机制（PPT 18.5 重点！）**：
  1. **撤销（Undo）与恢复（Redo）**：`Invoker` 维护一个**命令历史栈**，执行时压栈并调 `execute()`，撤销时弹栈并调 `undo()`。
  2. **宏命令（Macro Command / 组合命令）**：**组合模式 + 命令模式联用**的产物！一个宏命令包含多个子命令集合，调一次 `execute()` 递归批处理多个命令。
  3. **请求日志与排队**：利用 `CommandQueue` 排队；把命令对象**序列化（实现 `Serializable`）**写入日志文件实现断电恢复与防重复执行。
- **优缺点 & JDK 应用**：
  - ✅ **优点**：将**请求发送者与接收者完全解耦**；新增命令**符合 OCP**；易做命令队列、宏命令、Undo/Redo。
  - ❌ **缺点**：**可能导致系统产生过多的具体命令类**（每一个操作都要写一个命令类）。
  - 案例与应用：开关控制电灯/风扇、**功能键自定义（通过 XML 配置文件换绑功能）**、**电视机遥控器按钮（开/关/换台封装请求）**；Java **`Runnable` / 线程池**、**AWT/Swing 委派事件模型（DEM）**。

### 14. 迭代器模式（Iterator）
- **分类与地位**：GoF **对象行为型**模式（最简单、使用频率最高的行为型之一 ★★★★★）；别名**游标（Cursor）模式**。
- **官方定义（背诵）**：提供一种方法来**访问一个聚合对象**中的各个元素，而**不用暴露这个对象的内部表示**。
- **核心设计原则**：聚合对象原本承担“存储数据 + 遍历数据”两项职责，迭代器模式**将数据存储和数据遍历分离**（聚合类只存数据，迭代器只遍历），**完全符合单一职责原则（SRP）**！
- **核心角色（4 个）**：
  1. `Iterator`（抽象迭代器）：声明 `first()`、`next()`、`hasNext()`、`currentItem()`；
  2. `ConcreteIterator`（具体迭代器）：维持对 `ConcreteAggregate` 的引用和当前游标 `cursor`；
  3. `Aggregate`（抽象聚合类）：声明创建迭代器的工厂方法 `createIterator()`；
  4. `ConcreteAggregate`（具体聚合类）：存储元素并返回对应的具体迭代器 `return new ConcreteIterator(this);`。
- **优缺点 & 陷阱**：
  - ✅ **优点**：支持在同一聚合对象上**定义多种遍历方式**（正序/逆序）；简化聚合类；新增聚合类或迭代器类方便（**符合 OCP**）。
  - ❌ **缺点**：**新增聚合类时需要对应增加新迭代器类，类的个数成对增加**（⚠️ **判断坑**：“新增聚合类可以直接复用已有迭代器” -> **× 错误**！）；设计考虑全面的抽象迭代器难度较大（往里加新遍历方法会违背 OCP）。
- **PPT 案例 & JDK 应用**：
  - 案例：**电视机遥控器（按顺序遍历频道集合）**、销售管理系统（重构 `AbstractObjectList` 把遍历提取给 `AbstractIterator`）。
  - JDK 应用：**`java.util.Collection.iterator()`**、**`java.util.Iterator`**（`hasNext()`, `next()`, `remove()`）、`List.listIterator()`、Java 增强 `for-each` 循环。

---

### 15. 观察者模式（Observer）
- **分类与地位**：GoF **对象行为型**模式（★★★★★ 超高频大题王者）；
- **四大别名（填空高频！）**：**发布-订阅（Publish/Subscribe）模式**、**模型-视图（Model/View）模式**、**源-监听器（Source/Listener）模式**、**从属者（Dependents）模式**。
- **官方定义（背诵）**：定义对象间的一种**一对多依赖关系**，使得**每当一个对象状态发生改变时，其相关依赖对象皆得到通知并被自动更新**。
- **核心角色（4 个）**：
  1. `Subject`（抽象目标 / 被观察者）：维持 `ArrayList<Observer>` 集合，提供 `attach(Observer)`（注册）、`detach(Observer)`（注销）、抽象 `notify()`（通知）；
  2. `ConcreteSubject`（具体目标）：状态变化时循环遍历集合调用每个观察者的 `update()`；
  3. `Observer`（抽象观察者）：声明更新接口 `update()`；
  4. `ConcreteObserver`（具体观察者）：实现收到通知后的具体响应动作。
- **优缺点 & 必背考坑**：
  - ✅ **优点**：实现**表示层与数据逻辑层分离**；建立目标与观察者的**抽象耦合**；支持**广播通信**；增新观察者符合 **OCP**。
  - ❌ **缺点（判断高频坑！）**：
    1. 观察者太多时逐一通知**花费时间长**；
    2. 目标与观察者存在**循环依赖**时会导致系统崩溃（死循环）；
    3. **没有相应的机制让观察者知道所观察的目标对象是“怎么发生变化”的**，只知道它“发生了变化”！（❌ 判断题说“观察者知道目标怎么变化的” -> 错！）
    4. 若具体观察者直接关联具体目标属性，则增新目标时会违背 OCP。
- **PPT 案例、JDK 与真题应用**：
  - 案例：红绿灯与车辆、**猫叫老鼠跑狗也叫**、多人联机游戏（队友被攻击通知盟友触发链）。
  - **2023 期末真题压轴大题（排雷！）**：机房温度传感器 `ThermoSensor` 达阈值通知 `CautionLight`（警示灯）、`Annunciator`（报警器）、`ExitGate`（安全门） -> **绝对是观察者模式，不是策略模式！**
  - JDK & 架构应用：**Java 委派事件模型 DEM**（事件源、事件监听器、事件对象三要素，如 `button.addActionListener(...)`）、**经典 MVC 架构（Model = 目标，View = 观察者，Controller = 中介者）**。

---

### 16. 状态模式（State）
- **分类与地位**：GoF **对象行为型**模式；别名**状态对象（Objects for States）**。
- **官方定义（背诵）**：允许一个对象在**其内部状态改变时改变它的行为**，**对象看起来似乎修改了它的类**。
- **核心角色（3 个）**：
  1. `Context`（环境类）：**维持一个当前抽象状态 `State` 引用**（以及决定状态的业务属性值），把与状态相关的请求委托给 `state.handle()`；
  2. `State`（抽象状态类）：声明不同状态下的统一业务方法；
  3. `ConcreteState`（具体状态类）：实现该状态下的特定行为，并在满足条件时切换 `Context` 的当前状态。
- **PPT 重要分类（16.5 模式扩展）**：
  - **简单状态模式**：状态相互独立**无须转换**，客户端直接 `context.setState(...)`，遵循 OCP。
  - **可切换状态的状态模式（常见考点）**：状态切换可由 **① 环境类 `Context` 统一充当状态管理器切换**，或由 **② 具体状态类 `ConcreteState` 内部调用 `ctx.setState(new NextState())` 自行流转**。
  - **共享状态**：若多个 `Context` 共享同一状态对象，把状态对象定义为环境类的 **`static` 静态成员**。
- **优缺点 & 设计原则**：
  - ✅ **优点**：封装了状态转换规则，可集中管理；把每个状态的行为放进独立类，**消除庞大的 `if-else / switch-case` 条件语句块**；多个环境可共享状态对象。
  - ❌ **缺点（考坑！）**：增加类和对象个数；结构复杂易混乱；**对开闭原则（OCP）支持并不太好**（因为状态之间存在流转跳转关系，新增状态往往需要修改负责状态转换的旧状态类或环境类源码！）。
- **PPT 案例与代码**：电梯状态流转（开门/关门/运行/停止）、客房预订（空闲/已预订/已入住）、论坛用户等级（新手/高手/专家）、银行信用卡状态（正常/透支/受限）、OA 批文审批流、RPG 游戏人物状态。

### 17. 策略模式（Strategy）
- **分类与地位**：GoF **对象行为型**模式；别名**政策（Policy）模式**（提供一种**可插入式 Pluggable 算法**实现方案）。
- **官方定义（背诵）**：**定义一系列算法，将每一个算法封装起来，并让它们可以相互替换**。策略模式**让算法独立于使用它的客户而变化**。
- **核心角色（3 个）**：
  1. `Context`（环境类）：维持一个抽象策略类 `Strategy` 的引用，负责调用策略算法（**不负责挑，客户塞给它哪个就用哪个**）；
  2. `Strategy`（抽象策略类）：定义所有支持算法的公共接口；
  3. `ConcreteStrategy`（具体策略类）：实现某一个具体算法。
- **优缺点 & 必背考坑（题库简答题常考！）**：
  - ✅ **优点**：**提供对开闭原则（OCP）的完美支持**（增加新算法不改原系统）；管理相关算法族；**替代继承关系**；**避免多重条件选择语句（`if-else`）**；提供算法复用机制。
  - ❌ **缺点（3 条原话必背，多选/简答高频！）**：
    1. **客户端必须知道所有的策略类**，并自行决定使用哪一个策略类；
    2. 将造成系统**产生很多具体策略类**；
    3. **无法在客户端同时使用多个策略类**（每次只注入替换一个）。
- **PPT 案例 & JDK 应用**：
  - 案例：旅游出行方式（飞机/火车/自行车）、数组排序策略（冒泡/选择/插入）、**影院售票打折系统**（学生8折/儿童减10元/VIP半价）、促销员促销活动。
  - JDK 应用：**Java SE 容器布局管理器（`LayoutManager`：`FlowLayout`、`BorderLayout`、`GridLayout` 等）**。

### 🔥 行为型双胞胎终极辨析：策略模式 vs 状态模式（PPT 原表！）

| 对比维度 | 策略模式（Strategy） | 状态模式（State） |
| :--- | :--- | :--- |
| **核心意图** | 封装可互换的**算法**，让客户选择 | 让对象随**内部状态**改变而改变行为 |
| **客户端角色** | **主动**选择并注入具体策略 | **被动**调用方法，通常不了解具体状态 |
| **策略/状态间关系** | 彼此**独立、毫无关联** | 存在**流转依赖**（知道下一个状态是谁） |
| **切换控制权** | 由**客户端**外部控制切换 | 由**环境类或具体状态对象自身自动**切换 |
| **开闭原则支持度** | ✅ **完美支持 OCP** | ❌ **对 OCP 支持不太好**（新增状态常改切换逻辑） |
| **生动类比** | 去旅游**选择出行工具**（飞机/高铁自己挑） | 人的**心情/电梯状态自动转换**（喜怒哀乐触发转变） |

## 🎯 第五站：考场“易混双胞胎 & 反向排雷”最后 5 分钟速记

考场选择题最爱拿**同一个例子**或**相似概念**来混淆你，务必把下面这 6 组“双胞胎”分清：

1. **📺 电视机遥控器出现两次，别混！**
   - 题干说“遥控器**遍历、切换下一个/上一个电视频道集合**，不暴露电视内部集合结构” 👉 **迭代器模式**；
   - 题干说“遥控器上的**按钮（开/关/换台）向电视发请求**，解耦按钮和电视” 👉 **命令模式**。
2. **🔌 JDBC 出现三次，别混！**
   - 题干强调“**JDBC 驱动**把数据库厂商不同接口适配成统一 JDBC 接口” 👉 **适配器模式**；
   - 题干强调“应用程序维度 × 不同数据库实现维度**动态绑定解耦**” 👉 **桥接模式**；
   - 题干强调“自己封装一个 `JDBCUtil` 类把 `Connection/Statement/ResultSet` 统一成一个简单入口” 👉 **外观模式**。
3. **🖱️ Java GUI（AWT/Swing）出现四次，别混！**
   - `Component` 与 `Container` 构成**树形控件嵌套** 👉 **组合模式**；
   - `new JScrollPane(list)` 给列表**动态加滚动条** 👉 **装饰模式**；
   - `LayoutManager` 让容器**自由切换多种布局算法** 👉 **策略模式**；
   - `Button.addActionListener(...)` 按钮触发事件**通知多个监听器** 👉 **观察者模式** *(PPT 命令模式中也提到了 DEM 事件处理中监听类把请求封装成回调对象)*。
4. **🏷️ 一对“空接口 / 标识接口”**
   - 浅克隆 `Object.clone()` 必须实现 **`Cloneable`** 标识接口（否则抛 `CloneNotSupportedException`）；
   - 深克隆（序列化方式）和命令日志序列化必须实现 **`Serializable`** 标识接口。
5. **🏷️ 全课程所有“别名”一网打尽（填空送分题！）**
   - 简单工厂 = **静态工厂方法** / 上帝类
   - 工厂方法 = **虚拟构造器** / **多态工厂**
   - 抽象工厂 = **Kit 模式**
   - 适配器 = **包装器 (Wrapper)**；缺省适配器 = **单接口适配器**
   - 桥接 = **柄体 (Handle and Body)** / **接口模式**
   - 外观 = **门面模式**
   - 远程代理 = **大使 (Ambassador)**
   - 命令 = **动作 (Action)** / **事务 (Transaction)**
   - 迭代器 = **游标 (Cursor)**
   - 观察者 = **发布-订阅** / **模型-视图** / **源-监听器** / **从属者**
   - 状态 = **状态对象 (Objects for States)**
   - 策略 = **政策 (Policy)**
6. **⚠️ 全课程“结构最简单 / 最复杂”排序（2023 真题填空原话！）**
   - 创建型中结构最简单：**单例模式**（第1简）；其次是**原型模式**（简单程度仅次于单例模式和迭代器模式）；
   - 创建型中最复杂：**建造者模式**（难度 ★★★★★）；
   - 整体三大模式难度最低（★☆☆☆☆）：**单例**、**外观**、**策略**。
